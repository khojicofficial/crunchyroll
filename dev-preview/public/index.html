What the Crunchyroll page script does

Detection Where it comes from
isSyncPage() URL part 3 or 4 equals watch — i.e. /watch/<id>/<slug>
getTitle() episode_metadata from the proxied CMS response: series title plus the season suffix for later seasons, lower-cased
getEpisode() episode_metadata.episode_number (media id + slug fallback)
getIdentifier() series_id and season_slug_title, i.e. GY9P765D1|solo-leveling
nextEpUrl() episode links of the rendered episode list
isOverviewPage() URL part 3 or 4 equals series
overview.getTitle() h1 + active option of the season selector, matched against the seasonsGlobal list from /cms/series/<id>/seasons

What is real, what is faked

  • Real: ChibiProxy, ChibiListRepository, ChibiConsumer and the compiled pages/Crunchyroll.json from the build — the same interpreter the extension ships, executing the same AST.
  • Real: content/proxy/proxy_request.js is injected into the mock page and intercepts its fetch(), exactly like on crunchyroll.com.
  • Real: the popup bundle, its Vue app, its settings, its manifest and its provider list logic (_provider/listFactory), fed by mocked MAL API answers.
  • Faked: the Crunchyroll site itself (layout + DOM hooks), the Crunchyroll CMS responses, the MAL API payloads and api.* (extension storage / background messaging) — see dev-preview/src/apiStub.ts and dev-preview/public/popup-shim.js.
  • Sandbox quirk: proxy_request.js replays everything it buffered in one burst once the content script connects, and all those callbacks share a single chibi context, so only the last URL of the burst is seen. The mock site therefore re-fetches the episode payload on malsync-xhr-start — the same thing that happens on the real site whenever you navigate between episodes.
Smoke tests: node dev-preview/test/smoke.mjs (Crunchyroll pages) and node dev-preview/test/popup-smoke.mjs (popup).
